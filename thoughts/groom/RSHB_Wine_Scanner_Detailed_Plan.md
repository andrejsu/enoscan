# План разработки сканера российских вин
### Подготовка решения кейса РСХБ Цифра для максимальной оценки
**15 сентября 2026 года**

**Основную часть усилий направляем на точное определение позиции каталога по полевой фотографии. Одновременно доводим до готовности полезный сценарий после поиска, мобильную карточку и воспроизводимый запуск. Ключевое преимущество решения должно подтверждаться на почти одинаковых этикетках разных вин и годов.**

## 1 Приоритеты по критериям

| Критерий | Баллы | Что предъявляем экспертам |
| :--- | :---: | :--- |
| **Достоверность** | **50** | **Прогон по всем фотографиям; точный slug; F1 по правилам кейса; отдельный разбор похожих этикеток.** |
| **Функция после поиска** | **20** | **Рабочий подбор под блюдо и вкус, объяснение рекомендации, сохранение результата и повторное использование.** |
| **Архитектура** | **15** | **Разделённые компоненты, единый поиск для API и UI, воспроизводимый импорт и запуск на чистой машине.** |
| **Дизайн** | **10** | **Мобильный модуль в стилистике существующего каталога; законченные состояния загрузки, результата и ошибок.** |
| **Скорость** | **5** | **Измерения полного запроса на компьютере команды, распределение задержки и отсутствие таймаутов.** |

Вес критериев взят из раздела 7 ТЗ [1]. Формула перевода точности в конкурсные баллы не указана: 95% совпадений нельзя автоматически назвать 47,5 балла из 50. Цель плана — закрыть критерии доказуемо, без обещания заранее известного результата.

### Как скорректировать исходную стратегию
- Работающий end-to-end нужен первым. После него главным потоком становится повышение точности; уровень «хоть как-то ищет» недостаточен для максимальной оценки.
- Архитектуру оценивают за границы компонентов и воспроизводимость. Близость к рекомендованному стеку помогает внедрению, но не заменяет эти требования.
- Дизайн сравнительно недорогой по времени, однако максимальные баллы потребуют соответствия порталу и проверки на телефоне.
- Скорость оптимизируем после измерений. Пять баллов дают повод не жертвовать точностью ради миллисекунд, но таймауты и зависания могут испортить и поиск, и демо.

*Рабочий график предполагает три роли и пять рабочих дней. Это оценка для планирования; после получения данных, срока и характеристик оборудования её нужно уточнить.*

## 2 Требования и вопросы организаторам

Сервис должен идентифицировать конкретную запись каталога. Совпадения винодельни, серии или внешнего оформления недостаточно, если правильный ответ отличается годом или категорией. Такая постановка соответствует *instance retrieval* — поиску конкретного объекта по изображению.

### Что обязательно по заданию
- **CV-компонент поиска**: фотография из камеры или галереи; карточка из каталога в JSON; мобильный интерфейс в стилистике «Своё Вино».
- **Каталог**: примерно из 1500–2000 записей, по одной эталонной фотографии; публичные полевые фотографии и закрытая проверочная выборка.
- **Для Bash-скрипта**: один лучший результат, плоский JSON с единственным полем `slug`. Скрипт измеряет время самостоятельно.
- **Сценарий отсутствующего вина**: честный отказ либо предложение похожих вин или аналогов. Аналоги особенно приветствуются.
- **Ориентир совпадений**: 90–100%; SLA до трёх секунд. Проверка проходит локально на оборудовании команды; отдельный публичный деплой не требуется.
- **Материалы сдачи**: открытый для экспертов репозиторий, `README.md`, `ARCHITECTURE.md`, демонстрация без монтажных склеек и питч до семи минут. В финале фиксируется версия решения [1].

### Уточнить до настройки моделей

| Вопрос | Почему влияет на результат |
| :--- | :--- |
| **Точный endpoint, HTTP-метод, имя поля файла, таймаут, размеры изображений?** | Проверять совместимость по реальному скрипту; его отсутствие нельзя компенсировать догадкой об API. |
| **Как определяются F1 для top-1 и top-5, averaging и общий confidence?** | F1 требует правильных ответов; оценки похожести для одного запроса имеют другую семантику. |
| **Есть ли неизвестные вина в закрытом тесте и какой ответ допустим?** | Не вводить null, unknown или HTTP 404 в оценочный API без согласования. |
| **Как размечаются визуально неразличимые годы и одинаковые изображения с разными slug?** | Узнать, засчитывается ли группа эквивалентных карточек и есть ли информация для точного различения. |
| **Какой файл каталога окончательный и как получить изображения?** | В ТЗ встречаются JSON и CSV. Нужны реальные поля, URL или архив и версия данных. |
| **Можно ли обучаться на публичных фото и использовать внешние данные?** | Определить разрешённый train/dev и защитить итоговую оценку от утечки. |

*Дополнительно уточнить срок, доступ к GPU и условия онлайн-прогона. В требованиях промежуточного этапа UI одновременно перечислен и назван необязательным: для максимальной оценки планируем готовый интерфейс независимо от этой неоднозначности.*

## 3 Каталог и честная проверка

### Аудит данных
Импортёр должен сохранить исходный `slug` без пересоздания и привести данные к внутренней модели: название, производитель, серия, год, цвет, категория, сорта, регион, описание, изображение, рейтинги с указанием их типа, гастросочетания и температура подачи при наличии. Неизвестные значения остаются пустыми.

1. **Проверка целостности**: Уникальность `slug`, число записей, доступность изображений, размеры, повреждённые файлы и пустые поля. Сохранить отчёт импорта.
2. **Поиск дубликатов**: Посчитать хеши исходных файлов и найти полностью одинаковые эталоны. Отдельно сгруппировать похожие изображения и проверить различия в метаданных.
3. **Сложные семейства**: Подготовить перечень сложных семейств: одна винодельня и линейка, разные годы, сорта, категории или варианты Reserve. Семейства использовать для анализа ошибок и кандидатов.
4. **Версионирование**: Зафиксировать версию каталога и соответствие `image_id` — `slug`. Любые исправления данных должны оставаться видимыми в журнале.

### Разделение эталонов и полевых фотографий
- **Эталонная галерея**: Содержит весь выданный каталог. Из неё не удаляют вина, попавшие в проверку: поиск должен иметь возможность вернуть их `slug`. Делить нужно полевые запросы для экспериментов, а не случайно лишать тест его эталонов.
- **Сплит выборки**: При достаточном количестве публичных данных выделяем набор настройки и отложенную проверку (например, 70/30). Точная пропорция зависит от числа фото и групп. Все снимки одной съёмочной серии и производные одного исходника держим вместе.
- **Защита от утечек**: Полевые фотографии из отложенной проверки и их преобразования не включаем в поисковый индекс и обучение. Синтетические варианты эталонов помогают обучению, но не заменяют оценку на реальных снимках.

### Наборы для диагностики

| Срез | Что проверяем |
| :--- | :--- |
| **Обычные фото** | Чёткая этикетка, один объект, нормальный свет. |
| **Сложная съёмка** | Наклон, блики, темнота, размытие, маленькая этикетка, фон полки. |
| **Почти одинаковые вина** | Правильный год, сорт, категория, линейка; точный slug внутри семейства. |
| **Вне каталога** | Способность воздержаться от неверной идентификации и показать честные альтернативы. |

*Если публичная выборка мала, используем групповую кросс-проверку и явно показываем размеры срезов. Закрытую выборку организаторов не используем для подбора параметров.*

## 4 Визуальный поиск и нормализация

### Первый рабочий поиск (Baseline)
- За основу берём **SigLIP 2** (google/siglip2-base-patch16-384) [2].
- Один раз обработать эталоны штатным процессором модели, получить image embeddings и нормализовать длину векторов. Связать каждый вектор со `slug`.
- На запросе декодировать фото, учесть EXIF-ориентацию, привести к RGB и извлечь признаки тем же процессором и той же версией модели.
- Ранжировать галерею по косинусному сходству. Сохранить top-5 и более широкий список кандидатов для дополнительной проверки.

### Преобразования и нормализация

| Преобразование | Ограничение |
| :--- | :--- |
| **Выделение бутылки или этикетки** | Не обрезать мелкий год и дополнительные обозначения. Если автоматический кроп ненадёжен, сохранить исходное фото и запас вокруг области. |
| **Исправление наклона и перспективы** | Применять при надёжно найденной геометрии. Одна гомография не устраняет всю деформацию цилиндрической бутылки. |
| **Мягкая коррекция света и контраста** | Сохранять цвет и мелкие надписи; сильная обработка может ухудшать различение этикеток. |
| **Несколько представлений** | Сравнить полный кадр и кроп. Дополнительные варианты увеличивают время — учитывать прирост качества и задержки. |
| **Умеренные аугментации эталонов** | Поворот, освещение, перспектива. Не зеркалить надписи, не генерировать новые годы и детали. |

### Размер списка кандидатов
- Начинаем с 20–50 уникальных `slug` и измеряем Recall@K. Если правильный `slug` не попал в этот список, последующее уточнение его не восстановит.
- На 1500–2000 позициях сначала используем точный поиск по векторам. `pgvector` поддерживает его без приближённого индекса; HNSW и IVFFlat меняют компромисс между полнотой поиска и скоростью [3].

## 5 Различение похожих этикеток

Главный вопрос после baseline: ошибается ли модель в выборе семейства вина или путает записи внутри правильного семейства?

### Проверка текста у кандидатов (OCR)
- Извлекаем текст с эталонов и нормализуем метаданные: регистр, пробелы, варианты написания производителя и сорта. Год и категорию сохраняем как отдельные признаки.
- Для OCR используем **PaddleOCR** или аналогичный движок с поддержкой кириллицы и латиницы [6].
- На полевом фото OCR запускаем адаптивно: если top-1 и top-2 близки, кандидаты относятся к одному сложному семейству, либо изображение не даёт достаточного основания для уверенного ответа.
- Сопоставлять распознанные данные только с реальными кандидатами каталога.
- Различать год урожая, год основания винодельни и другие числа. Явное надёжное несовпадение года штрафует кандидата сильнее, чем обычное отсутствие текста.

### Порядок ранжирования кандидатов (Reranker)
- Начальный reranker объединяет визуальное сходство, совпадение ключевых надписей и штраф за надёжные противоречия.
- Вторую модель или дообучение добавляем только при подтверждённой пользе на наборе ошибок.
- **Условие дообучения**: baseline, нормализация и OCR уже измерены; ошибки относятся к представлению изображения; есть разрешённые данные.

*Если у двух записей одинаковая видимая этикетка, а год скрыт на контрэтикетке, по одному снимку его определить нельзя. Такие примеры документируем и в продукте просим дополнительный снимок.*

## 6 Метрики и уверенность

F1 характеризует сопоставление предсказаний с правильными ответами. В многоклассовом случае способ усреднения меняет смысл метрики (micro, macro, weighted) [4].

### Минимальный отчёт

| Показатель | Что означает | Рабочая цель |
| :--- | :--- | :--- |
| **Accuracy@1** | Доля запросов с точным правильным slug на первом месте. | Ориентир 95% и выше; минимум из ТЗ 90%. |
| **F1 top-1** | F1 по согласованному усреднению и правилам обработки отказов. | Считать точно по формуле организаторов. |
| **Recall@5** | Доля запросов, у которых правильный slug есть среди 5 результатов. | Стремиться к 98–100%. |
| **Recall@K** | Попадание правильной карточки в список до уточнения. | Достаточно высокий для работы reranker. |
| **Accuracy на похожих винах** | Точность внутри групп почти одинаковых этикеток. | Рост относительно baseline. |
| **Автоответы и отказы** | Доля автоматических карточек, их точность, ложные совпадения. | Показывать вместе; не скрывать ошибки ростом отказов. |
| **Задержка** | Весь запрос: p50, p95, максимум, таймауты; холодный запуск. | SLA до 3 сек; p95 до 3 сек как внутренняя цель. |

*При единственной правильной карточке и пяти выданных, precision равен 1/5, recall равен 1, а F1 равен 1/3. Выдавать Recall@5 под названием F1 нельзя.*

### Диагностика запроса
- Храним оценки кандидатов: `score`, `margin` (разница между 1-м и 2-м), признаки совпадения OCR и длительность этапов.
- Пороги проверяем по абсолютной оценке, отрыву, текстовым противоречиям и фактическим ошибкам.

## 7 Архитектура и воспроизводимость

Рекомендуемая реализация: **Nuxt** с серверным API, Python-сервис CV (**FastAPI**), **PostgreSQL** с **pgvector** и адаптер каталога **Strapi**.

### Компоненты и ответственность

| Компонент | Ответственность |
| :--- | :--- |
| **Nuxt и серверный API** | Мобильные экраны, загрузка, чтение карточки, сценарий после поиска, внешний контракт. |
| **Python и FastAPI** | Обработка изображения, энкодер, OCR, уточнение кандидатов, единый SearchService. |
| **PostgreSQL и pgvector** | Каталог, векторы, версии данных; история и сохранённые подборки. |
| **Адаптер каталога** | Приведение CSV/JSON к внутренним полям; путь интеграции со Strapi. |
| **Инструменты оценки** | Официальный Bash-скрипт без изменения его логики; локальный отчёт по всем запросам. |

### Структура репозитория
- `apps/web/`: Nuxt, страницы, компоненты, серверные маршруты.
- `services/retrieval/`: normalization, encoders, candidate_search, reranking, confidence, API.
- `packages/contracts/`: Схемы входов и ответов; преобразование результата в один slug.
- `scripts/`: Импорт, построение индекса, прогон оценки, отчёт.
- `configs/` и `reports/`: Параметры экспериментов; метрики и журнал ошибок.
- `README.md` и `ARCHITECTURE.md`: Запуск, ограничения; компоненты, данные и движение запроса.

## 8 Контракты и обработка ошибок

### Оценочный маршрут
- Формат ответа: плоский JSON `{"slug": "wine-slug"}`.
- Ответ должен точно соответствовать контракту: один лучший slug, без обёртки data или дополнительной диагностики.

### Продуктовый маршрут

| Поле / Группа | Смысл |
| :--- | :--- |
| **status** | `matched`, `uncertain` или `not_found`. |
| **wine** | Настоящая карточка каталога при совпадении; иначе `null`. |
| **candidates** | До 5 уникальных slug с оценками для диагностики. |
| **confidence** | Тип оценки, top1_score, margin; calibrated_probability. |
| **timing** | Время по этапам: декодирование, CV, поиск, OCR, уточнение, общий ответ. |
| **alternatives** | Рекомендации при неизвестном вине. |
| **version** | Версии модели, каталога и конфигурации. |

### Ключевые проверки
- Корректное фото возвращает допустимый slug каталога и HTTP 200.
- Повреждённый файл или неверный формат дают понятную ошибку с правильным HTTP-кодом.
- Таймаут OCR не блокирует поиск: есть зафиксированный фоллбек к CV-результату.
- Сбой необязательного LLM не мешает открыть карточку.

## 9 Дополнительная функция после поиска

Предлагаем функцию **«Подойдёт ли к моему ужину»** (подбор вина к блюду и вкусу).

### Основной сценарий
1. В карточке найденного вина — кнопка «Подобрать к ужину».
2. Шаг 1: Выбор блюда из понятных категорий или короткого ввода.
3. Шаг 2: Указание предпочтения по вкусу (более мягкое / насыщенное).
4. Результат: Пояснение совместимости, обоснование и 2–3 альтернативных карточки из каталога.
5. Сохранение: Подборка сохраняется в «Моих сочетаниях».

### Техническая реализация
- Работает на структурированных данных каталога и проверенных правилах (без обязательного LLM).
- LLM используется как опциональное улучшение текста объяснения.
- События аналитики: `scan_matched`, `pairing_started`, `pairing_completed`, `pairing_saved`, `saved_pairing_opened`.

## 10 Мобильный интерфейс и скорость

### Дизайн в стилистике «Своё Вино»
Используем существующие цвета, шрифты, кнопки и иконки портала «Своё Вино» [5].

| Состояние UI | Что проверяем |
| :--- | :--- |
| **Старт** | Камера и галерея, подсказка о положении этикетки, понятный шаг. |
| **Обработка** | Анимация загрузки, блокировка повторных отправок. |
| **Успех** | Карточка с производителем, названием, годом, регионом, сортом, описанием. |
| **Неуверенность** | Просьба переснять год или убрать блик; отсутствие ложной уверенности. |
| **Нет в каталоге** | Честное сообщение и аналоги. |
| **Ошибка** | Возможность повторить запрос или выбрать другой файл. |
| **Сценарий фичи** | Вопросы подбора, объяснение, сохранение и открытие. |

### Оптимизация скорости (SLA < 3 сек)
- Модель и OCR загружаются при старте сервера (warmup).
- Эталонные векторы вычисляются заранее.
