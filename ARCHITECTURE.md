# Архитектура Vinolog

## Границы системы

```text
Мобильный браузер
      ├─ multipart/form-data ──► Nuxt scans API ──► Ranking API (FastAPI)
      │                                                ├─ OCR retriever: RapidOCR → per-field
      │                                                │  candidates (name/winery/year/…),
      │                                                │  scored against catalog vocabulary
      │                                                ├─ Visual retriever: DINOv2 + SIFT/FLANN
      │                                                │  + RANSAC → slug candidates
      │                                                └─ rank(): weighted field match → one
      │                                                   slug, or an honest not_found
      │
      ├─ (admin, /astro, image proxy) ──► PostgreSQL catalog / MinIO
      └─ JSON chat ───────────► Nuxt sommelier API ──► AI provider
                                      │                    (server-side only)
                                      └─ parameterized SQL tool
                                                   │
                                                   ▼
                                              PostgreSQL catalog

data/dataset (CSV, RAR, eval) ──► importer ──┬─► PostgreSQL (pgvector): wines, images, wine_images,
                                             │     import_runs, index_builds, image_embeddings
                                             └─► MinIO: оригиналы и превью (sha256), SIFT-индексы, eval
```

- `apps/web/app` отвечает за интерфейс и состояние пользовательского сценария.
- `apps/web/server/api` валидирует HTTP-ввод и переводит результат внешнего сервиса в продуктовый контракт. CV-логика здесь не размещается.
- `apps/web/shared/contracts` — единственный источник форм ответов между слоями.
- `services/importer` — единственный writer каталога и картинок: миграции, версия датасета, картинки и превью в MinIO, привязка фото к винам.
- `services/retrieval` содержит несколько независимых FastAPI-сервисов из одного пакета `app/` (см. `services/retrieval/README.md`): `retrieval` — чисто визуальный SIFT-поиск; `retriever` — визуальный DINOv2+SIFT поиск; `ocr-retriever` — единственное место, где работает OCR (RapidOCR), отдаёт per-поле кандидатов, не резолвит вино; `ranking` — комбинирует OCR- и визуальные кандидаты в конкретный `slug` и стоит за продуктовым сканером. Ни один не знает о компонентах Nuxt, все только читают PostgreSQL и MinIO.
- `/admin` использует read-only server API Nuxt, который читает PostgreSQL напрямую: каталог, дубли исходных строк, привязку и проверку фото, состав текущего поискового индекса.
- `/astro-sommelier` использует тот же read-only PostgreSQL-каталог и выбирает карточки только из текущей сборки поискового индекса.
- `/sommelier` хранит историю локально в браузере; server API получает только ограниченное окно реплик и никогда не раскрывает ключ провайдера.

## Два контракта поиска

Продуктовый маршрут `POST /api/scans` (Nuxt) вызывает `ranking`'s `/v1/search`, который возвращает `matched` или `not_found` (без `uncertain` — у ранжирования бинарный порог уверенности, см. ниже), карточку, диагностические оценки и версии в том же контракте `ScanResponse`, что и раньше отдавал `retrieval`. Кандидаты могут содержать `wine` для ручного выбора в UI. Оценочный маршрут `ranking`'s `/v1/eval/predict` (порт 8080 — порт по умолчанию в `participant_test.sh`) проходит тот же `_scan` → `rank()`, что и `/v1/search`, и возвращает плоский JSON `{"slug":"..."}`. При `not_found` slug по политике `RANKING_EVAL_POLICY`: `matched` (по умолчанию) — пустая строка, которую скрипт записывает как `null`; `top1` — лучшее вино.

## OCR, визуальный поиск и объединение кандидатов

OCR и визуальный поиск — не единый блендированный скор внутри одного сервиса (как было раньше), а два независимых источника доказательств, каждый со своей зоной ответственности, объединяемые только на этапе ранжирования (`services/retrieval/app/search/ranking.py`). Общий стракт для обоих — `app/evidence.py`: `RetrievalFields` с полями `name`/`winery`/`grape_varieties`/`year`/`abv`/`category`/`sweetness`/`region`/`slug`, у каждого — ранжированный список кандидатов `(значение, оценка 0..1)`.

**OCR (пакет `app/ocr/`, сервис `ocr-retriever`).** RapidOCR 3.9: детекция PP-OCRv6 + кириллическое распознавание PP-OCRv5, ONNX на CPU, модели запечены в образ. Сначала читается центральный кроп кадра с учётом EXIF (`OCR_CROP_BOX`: 25–75 % по ширине, 15–90 % по высоте; у узких кадров вроде вырезанной бутылки — только по высоте), и только если в нём меньше трёх слов — полный кадр. У полки иначе смешивается текст соседних бутылок (на фото Массандры «МУСКАТ … КРАСНОГО» соседа вместо «МУСКАТЕЛЬ БЕЛЫЙ»), а детектор видит этикетку крупнее: на размеченных фото OCR занимает 1–3 с вместо 2–9 с. Tesseract на тех же фото почти ничего не читал. Латинские двойники кириллицы (`KPACHOE`, `ДЕHИCOB`, `3AKAT`) складываются обратно в кириллицу. Так же складываются греческие двойники (`ΟΛΕΓ` → «ОЛЕГ»), цифры внутри слова (`Py6uH` → «Рубин») и U вместо V в заглавной латинице (`UUA UALLIS` → «UVA VALLIS»). Служебные слова этикетки («семейная винодельня», «на территории Российской Федерации») не голосуют за название: иначе «ВИНОДЕЛЬНЯ» на любой этикетке выбирала единственные названия каталога с этим словом — Пет-Наты Ведерникова. Французские и итальянские написания сортов читаются как русская транслитерация каталога (Pinot Gris — «Пино Гри», Syrah — «Сира», Grigio — «Гриджио», Orange — «Оранж»). Если винодельня прочитана уверенно, название ищется и среди её вин: лучшее из них получает 1.0, названия других виноделен — половину своей оценки, так что «РОЗЕ» на этикетке Табии — её «Розе», а не одно из десятков «Розе» каталога. Возвращает строки текста, confidence и координаты. `ranking` вызывает сервис по HTTP параллельно с `retriever`; если недоступен один из двух, скан идёт по второму, если оба — 503. Для полей с закрытым словарём каталога (name/winery/grape_varieties/category/region) — fuzzy-поиск по всем различным значениям поля в каталоге (`app/ocr/vocabulary.py`), топ-10 по оценке. Слово, которое каталог знает, читается как есть и не совпадает нечётко с другими («МУСКАТЕЛЬ» — не «Мускат»); нечёткое совпадение остаётся для опечаток OCR. Слово сорта в одиночку не называет винодельню: «ПИНО» из «ПИНО НУАР» давало винодельню «Шато Пино» и полный голос всем её винам. Для year/abv — все прочитанные значения (не одно доверенное), оценка = confidence строки OCR. OCR никогда не резолвит вино сам.

**Визуальный поиск (`app/visual/retriever.py`, сервис `retriever`).** DINOv2-эмбеддинг + SIFT/FLANN голосование + RANSAC геометрическая проверка, комбинированный скор `0.45·SIFT + 0.55·embedding`. Отдаёт только одно поле — `slug`, топ-10 кандидатов: это прямое доказательство идентичности вина, разложение на текстовые поля было бы придуманным сигналом.

**Ранжирование (`app/search/ranking.py`, сервис `ranking`).** Сырые оценки полей несравнимы между собой (у зашумлённой этикетки верное название OCR может получить 0.28), поэтому каждое поле сначала превращается в распределение по своим кандидатам — softmax относительно top-1 поля (температура 0.05 для визуала, 0.06 для OCR). Top-1 поля получает большую часть массы, почти равные кандидаты делят её, кандидаты с низких позиций почти ничего не получают — поле, которое не различает кандидатов, не может их переставить. Блоки только помогают друг другу: скор вина — сумма `вес × доля голоса поля` по всем полям, делённая на постоянную сумму весов `FIELD_WEIGHTS`. Согласное поле повышает скор, поле без мнения об этом вине ничего не добавляет, но и не тянет вниз остальные; явное совпадение, которое подтверждают и визуал, и OCR, получает около 0.4–0.8. Цвет OCR не ищет: в каталоге это описательный текст («Нежный лососевый цвет…»), совпадения с ним — шум; «полусухое» на этикетке раньше уходило именно туда. Сахара (сухое, полусухое, полусладкое, сладкое, брют, экстра брют, брют натюр) в каталоге отдельной колонкой нет: `Wine.sweetness` выводится при загрузке каталога из названия, затем slug, затем имени исходного файла фото (`app/label_text/sweetness.py`) — есть у 84 % вин; у трёх «Жемчужная 9 Пино Нуар, Мускат Розовый» он есть только в имени файла («п.сл», «п.сух», «сух»). Тот же разбор читает сахар с этикетки в поле `sweetness`. В скор сахар не входит: «сухое» у 58 % каталога, как голос он ничего не различает. `matched` требует отрыва лидера от второго вина не меньше `RANKING_MIN_MARGIN` (по умолчанию 0.03; до 2026-09-25 — 0.06: на искажённых эталонах 0.03 даёт 28 неверных ответов против 14 при почти том же числе верных) и ненулевого свидетельства по названию (OCR) или визуальному `slug`; иначе — честный `not_found`, без промежуточного статуса. Общие поля (винодельня, сорт, категория, регион, год) влияют на порядок, но сами совпадение не дают. Год только подтверждает вино, чьё название OCR прочитал на этикетке: иначе «2022» поднимало в top-5 все вина с «2022» в названии, а слабое визуальное совпадение («Аврора 2024», 10 inliers) получало полный балл за год рядом с вином, которое этикетка называет. Веса, температуры и отрыв подобраны 2026-09-25 на 9 размеченных реальных фото и 147 искажённых эталонах каталога; это малая выборка, пересчитать при появлении новых размеченных фото.

**Сверка с этикеткой (`verify_shortlist`).** Поля только добавляют, поэтому визуальный лидер побеждал, даже когда этикетка ему прямо противоречит (Anima Blush против прочитанного «MILLESIMATO»). Перед решением с текстом OCR сверяются top-3 ранжирования и вина с лучшим названием OCR, даже если визуал их не нашёл (Массандра на полке: визуал видит только семейство этикеток, OCR читает «МУСКАТЕЛЬ БЕЛЫЙ»). Каждый блок может выдвинуть вино, решает этикетка. Кроме названия, года, категории, сахара и винодельни вино отклоняет сорт, который этикетка пишет полностью и точно («PINOT GRIS» против Мускат-брюта), — но только как лидера: соседа, который держит отрыв, сорт не убирает («VELVET SEASON MUSCAT» не делает уверенным Мускат Оттонель только потому, что Рислинг той же линейки отпал). «ОРАНЖ» на этикетке исключает вино, оранжевое ни по категории, ни по названию: 20 из 32 оранжевых вин каталог записал белыми, но у всех «Оранж» в названии. Противоречие по винодельне берёт первую из винодельн OCR, чьё отличительное слово видно на этикетке: «СЕМЕЙНАЯ ВИНОДЕЛЬНЯ ЛИТАВЩУКОВ» ставит первой ЛОРИО (по словам «семейная винодельня»), но написан там только «Литавщук». Прочитанное слово поддерживает только те слова шортлиста, с которыми совпадает лучше всего; названия каталога сравниваются между собой точно: «Мускатель» не засчитывается «Мускату». Вино отклоняется, если на этикетке есть длинное слово из названия соседа, которого нет в его собственном названии, и ни одно прочитанное слово не говорит за него; слова винодельни и стиля («брют», «экстра», «резерв») не считаются. Также вино отклоняется, если OCR прочитал ровно одну категорию, год или сахар и они расходятся с каталогом (уровни брюта между собой не противоречат: OCR может прочитать «BRUT» от «EXTRA BRUT»). Сахар разводит 13 групп вин с одинаковыми названием и винодельней, которые больше ничем не различаются. Ответ — лучшее по скору проверенное вино без противоречий; отклонённые уходят в конец списка, скоры не меняются. Отрыв считается от лучшего соперника, которого этикетка не опровергает; ближайший непроверенный соперник тоже сверяется, до 8 вин. Из гонки выбывают вина, опрокинутые этикеткой (были выше победителя), вина с противоречием по категории, году или сахару и — только когда этикетка показывает все отличительные слова названия победителя — вина, отклонённые по названию. Если победитель назван частично, отклонённое по названию вино ниже него остаётся соперником: этикетка может подходить и непроверенному соседу («Цитрон» у «Пет-Нат Цитрон-Ркацители» и «Петнат Цитрон – Рислинг»). Одним OCR, без визуального совпадения, вино опознаётся, только если этикетка показывает все отличительные слова его названия: «Пино Нуар полусухое» на бутылке Табии (её нет в каталоге) не совпадает с одноимённым вином Нового Света. Если этикетка противоречит всему шортлисту — `not_found`. Каждое проверенное вино с прочитанными словами его названия и вердиктом («подтверждено», «без возражений», «отклонено» с причиной) показывает блок «Сверка с этикеткой» debug-панели. Стенд 2026-09-25 (10 размеченных реальных фото и 147 искажений 21 эталона, OCR и визуальные кандидаты закешированы): F1 0.722 против 0.669 до сверки, 15 ошибочных ответов против 24; на реальных фото 9 из 10, ни одного ошибочного ответа. Десятое (Перовских «Полусухое») не находилось из-за данных: к вину было привязано фото игристого «Золотой Балки», а его настоящее фото — к `leto-risling-2024-polusuhoe-vino`; исправлено в `db/image-overrides.csv`. После этого `scripts/eval_ranking.py` на живом стеке: 10 из 10 (8 в каталоге, 2 вне его), F1 1.0, отрыв верных ответов 0.077–0.413 (медиана 0.147), у фото вне каталога 0.010 и 0.057 — оба `not_found`. Это 10 фото: пороги кропа и список слов стиля подобраны на них, на приватном наборе ждать тех же цифр нельзя.

**Отладочная трасса (`app/search/debug.py`).** При `RANKING_DEBUG=true` (по умолчанию) ответ `/v1/search` сервиса `ranking` содержит поле `debug` (контракт `ScanDebug` в `apps/web/shared/contracts`): превью кадра, визуальной ветки label_prep с метриками и кропа, который читал OCR, кандидаты OCR по каждому полю (до 10), top-10 ретривера с inliers/matches, сверку шортлиста с этикеткой (`verification`) и top-10 ранжирования с вкладом каждого поля. На странице результата его показывает раскрывающаяся панель `ScanDebugPanel` — и при найденном вине, и без него. Трасса не меняет скоры; единственное, что она пересчитывает, — кроп label_prep для превью; превью передаются как JPEG data URL (~100 КБ на ответ).

Порог отрыва проверен только на малой выборке (см. `scripts/eval_ranking.py`); синтетическая оценка и HTTP smoke не доказывают точность на приватном наборе.

## Текущий поток

1. Пользователь выбирает фото через файловый input с `capture="environment"`.
2. Клиент проверяет тип и размер, создаёт локальный preview и отправляет `FormData` в `/api/scans`.
3. Nuxt server route повторно валидирует файл.
4. При `NUXT_PUBLIC_SCAN_MODE=mock` маршрут возвращает маркированную демонстрационную карточку.

Астрологический сценарий изолирован публичным runtime-флагом `NUXT_PUBLIC_ASTRO_ENABLED`. Проверка выполняется во всех точках входа: навигации, карточке результата, middleware страницы и серверном API. При отключении API отвечает `404`, поэтому скрытие интерфейса не является единственной защитой функции. Так же изолирован каталог (`/admin`, `/api/admin/wines`) флагом `NUXT_PUBLIC_CATALOG_ENABLED`: инструмент проверки импорта, на проде по умолчанию выключен.
5. В Compose Nuxt проксирует сам запрос сканера через приватный `NUXT_RANKING_BASE_URL` в `ranking` — это финальный, объединённый результат OCR и визуального поиска. Оценочный маршрут `/v1/eval/predict` вызывается напрямую у `ranking` (порт 8080).
6. Карточки получают `imageUrl` и `imagePreviewUrl` только при наличии привязки в `wine_images`. `/api/wines/{slug}/image` находит основное фото в PostgreSQL и потоком отдаёт оригинал или превью из MinIO с `ETag` по sha256 — независимо от того, попал ли эталон в поисковый индекс какого-либо из сервисов поиска.
7. Админка запрашивает пагинированный `/api/admin/wines`: Nuxt строит выдачу SQL-запросом к `wines`, `wine_images` и `index_references` текущей сборки, независимо от `retrieval`/`retriever`/`ranking`.

## Поток цифрового сомелье

1. Клиент отправляет до 11 последних реплик в `/api/sommelier/chat`; сервер проверяет длину, роли и чередование общим Zod-контрактом.
2. Сервер применяет лимит сессии и локальную проверку мата. Завершённые социальные реплики вроде благодарности или «ладно» получают короткий ответ без поиска каталога; реплика с новым винным запросом проходит дальше. Текст заблокированного сообщения не записывается в лог.
3. В `live`-режиме выбранный через runtime config AI-провайдер классифицирует весь входной диалог. Поддерживаются OpenAI, Anthropic и Google через единый AI SDK adapter.
4. Модель формирует структурированные фильтры, после чего сервер обязательно вызывает `searchCatalog`. Тип вина ограничен реальными категориями базы; описательные слова ищутся русским полнотекстовым поиском. Если они обнулили выдачу, поиск повторяется без них, но сохраняет тип вина, регион, сорт и оттенок. Полностью нефильтрованный fallback запрещён.
5. Структурированный ответ содержит до трёх `slug`. Сервер принимает только `slug`, реально возвращённые поиском в текущем запросе, и повторно классифицирует текст ответа. Если модель проигнорировала непустую отфильтрованную выдачу, сервер показывает до трёх найденных карточек с нейтральным текстом.
6. В `mock`-режиме те же продуктовые состояния воспроизводятся локально и всегда маркируются в UI и API.

## Данные и индексы

Состояние хранится только в PostgreSQL (с pgvector) и MinIO. При каждом `docker compose up` одноразовый `importer` применяет миграции `db/migrations` и вычисляет `dataset_version` — хэш CSV, томов RAR, `db/image-overrides.csv` и версий алгоритмов привязки и превью. Если версия совпадает с последним успешным `import_runs`, работа пропускается. Иначе:

- оригиналы читаются из RAR по одному и кладутся в MinIO под sha256 содержимого вместе с превью; неизменный архив не перечитывается;
- каталог, привязка фото, ручные исправления и журнал проблем пишутся в PostgreSQL одной транзакцией.

Индексаторы работают по `dataset_version`. `retrieval-index` сохраняет `sift-v3/{version}.npz` в MinIO и регистрирует сборку в `index_builds`/`index_references`. `retriever-index` так же сохраняет SIFT-часть `retriever-v2`, а эмбеддинги DINOv2 пишет в `image_embeddings` (pgvector) по ключу sha256 картинки и модели, поэтому пересчитываются только новые картинки. Сервисы поиска при старте скачивают сборку для текущей версии. Ретривер ищет ближайшие эмбеддинги точным запросом pgvector в пределах своей сборки.

Для разработки web монтирует рабочую директорию проекта вместе с `.git` из хоста. Зависимости и генерируемые типы Nuxt живут в отдельных Docker volumes; Git использует SSH-настройки хоста или личный ключ через read-only mount. Entrypoint готовит права для UID/GID из локального `.env` перед запуском dev-сервера. Обычный `docker compose exec web sh` также открывает shell от этого пользователя; `psql` внутри него подключается к PostgreSQL. Постоянные тома — только `postgres-data`, `minio-data` и `retriever-models`.

## Требования к железу

Требования к компьютеру, на котором полный стек из `compose.yaml` (сканер, карточка, сомелье, маршруты) укладывается в SLA ответа ≤ 3 с.

- **GPU не нужен.** Весь инференс идёт на CPU через `onnxruntime`.
- **Нейросети в распознавании есть**, поэтому нужны и процессор, и память:
  - DINOv2-small (ONNX, 88 МБ) строит визуальные эмбеддинги этикетки;
  - RapidOCR (PP-OCRv5, кириллица, mobile) распознаёт текст;
  - SAM ViT-B (квантованная) сегментирует бутылку при построении индекса; для запросов по умолчанию выключена (`RETRIEVER_QUERY_SAM=false`).
- Внешний LLM нужен только сомелье в режиме `live`. Сам поиск по фото работает локально и без интернета.

| | Минимум | Рекомендуется (демо, замер SLA) |
|---|---|---|
| CPU | 4 ядра x86-64 с AVX2 или Apple Silicon | 8+ ядер (замер ниже — Apple M1 Pro, 10 ядер) |
| RAM компьютера | 12 ГБ | 16 ГБ |
| RAM, выделенная Docker | 8 ГБ | 10 ГБ |
| Диск | 30 ГБ свободно, SSD | 50 ГБ, NVMe SSD |
| GPU | не нужен | не нужен |
| Сеть | только при первой сборке | при первой сборке; для `live`-сомелье и карт — постоянно |

Минимум по CPU — оценка, на 4 ядрах мы не мерили. Ожидаем, что сервис заработает, но p95 выйдет за 3 с.

### Замер на текущем стенде

Стенд: Apple M1 Pro, 10 ядер, 16 ГБ; Docker Desktop, выделено 10 CPU и 7.75 ГБ RAM. Замер 2026-09-28.

**Память в простое** (все сервисы подняты, модели загружены):

| Сервис | Что делает | RAM |
|---|---|---|
| `retrieval` | базовый SIFT-поиск, индекс в памяти | 2.1 ГБ |
| `retriever` | DINOv2 + SIFT, визуальный шортлист | 1.9 ГБ |
| `web` | Nuxt (dev-режим в контейнере) | 1.6 ГБ |
| `ocr-retriever` | RapidOCR | 0.3 ГБ, пик 0.65 ГБ |
| `minio` | хранилище картинок | 0.23 ГБ |
| `ranking` | объединение кандидатов, решение `matched` | 0.08 ГБ |
| `db` | PostgreSQL 16 + pgvector | 0.05 ГБ |
| **Итого** | | **≈ 6.2 ГБ в простое, ≈ 6.6 ГБ под нагрузкой** |

Если выделить Docker меньше 8 ГБ, контейнеры начнёт убивать OOM-killer: чаще всего `retrieval` или `retriever`, и тогда healthcheck не проходит.

**CPU на один запрос** (пик за время запроса, 100% = одно ядро):

| Сервис | Пик CPU |
|---|---|
| `ocr-retriever` | ≈ 530% (5–6 ядер) |
| `retriever` | ≈ 250% (2–3 ядра) |
| `ranking`, `retrieval` | ≈ 70% |

OCR и визуальный поиск идут параллельно, поэтому один запрос кратковременно занимает около 8 ядер. Отсюда рекомендация 8+ ядер: на меньшем числе ядер время ответа растёт почти линейно. Если OCR не укладывается в `OCR_TIMEOUT_SECONDS` или `ocr-retriever` недоступен, `ranking` решает только по визуальным кандидатам, и точность падает.

**Время ответа** на размеченных реальных фото (`reports/eval/real-photos-ocr-v3.json`, 78 фото): p50 2.0 с, p95 2.6 с, max 3.8 с, 96% запросов в SLA. При контрольном замере с параллельно запущенным `docker stats` ответы заняли 3.7–7.4 с: сбор статистики сам отнимает CPU, а первые запросы идут на холодных моделях. Поэтому перед замером скорости:

- прогрейте сервис 2–3 запросами;
- закройте тяжёлые приложения: браузер с множеством вкладок, индексацию в IDE;
- для записи видео используйте запись экрана с аппаратным кодированием (стандартная в macOS такая): программное кодирование отнимает CPU у сервиса.

|---|---|

### Программное обеспечение

- **ОС:** Linux x86-64 или arm64, macOS 13+ (Intel или Apple Silicon), Windows 10/11 с WSL 2.
- **Docker:** Docker Engine 24+ с плагином Compose v2, или Docker Desktop.
  - macOS и Windows: в Docker Desktop → Settings → Resources выставьте не меньше 8 ГБ памяти и все доступные ядра. По умолчанию Docker Desktop даёт меньше, и стек не поднимется.
  - Linux: отдельной настройки нет, контейнеры используют память хоста напрямую.
- Локальный Node.js нужен только для запуска без Docker (`npm run dev`, mock-режим): Node.js 22.22.2+, npm 10+.
- Python 3 на хосте нужен только для скриптов оценки (`scripts/eval_ranking.py`).
- Скрипт оценки кейсодержателя — Bash: на Windows запускайте из WSL.

### Запуск на слабом компьютере

- Выключите необязательное: `NUXT_PUBLIC_ASTRO_ENABLED=false`, `NUXT_PUBLIC_CATALOG_ENABLED=false`, сомелье — `mock` или `off`. На поиск это не влияет, но немного разгружает `web`.
- `web` в `compose.yaml` работает в dev-режиме. Production-сборка (`deploy/compose.prod.yaml`) должна занимать меньше памяти; мы её отдельно не мерили.

## Инварианты

- Аналог не называется точным совпадением.
- `score` не называется вероятностью; `calibratedProbability` появляется только после калибровки.
- Инфраструктурная ошибка не превращается в `not_found`.
- Браузер не обращается к CV-сервису напрямую.
- Браузер не обращается к LLM-провайдеру напрямую; приватные ключи существуют только в server runtime config.
- AI не может вернуть карточку по `slug`, отсутствующему в результате последнего вызова каталога.
- Базовая карточка и локальные сохранения работают без LLM.
