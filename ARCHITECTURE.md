# Архитектура Vinolog

## Границы системы

```text
Мобильный браузер
      ├─ multipart/form-data ──► Nuxt scans API ──► Ranking API (FastAPI)
      │                                                ├─ OCR retriever: RapidOCR → per-field
      │                                                │  candidates (name/winery/year/…),
      │                                                │  scored against catalog vocabulary
      │                                                ├─ Visual retriever: DINOv2 + SIFT/FLANN
      │                                                │  + RANSAC → slug candidates
      │                                                └─ rank(): weighted field match → one
      │                                                   slug, or an honest not_found
      │
      ├─ (admin, /astro, image proxy) ──► PostgreSQL catalog / MinIO
      └─ JSON chat ───────────► Nuxt sommelier API ──► AI provider
                                      │                    (server-side only)
                                      └─ parameterized SQL tool
                                                   │
                                                   ▼
                                              PostgreSQL catalog

data/dataset (CSV, RAR, eval) ──► importer ──┬─► PostgreSQL (pgvector): wines, images, wine_images,
                                             │     import_runs, index_builds, image_embeddings
                                             └─► MinIO: оригиналы и превью (sha256), SIFT-индексы, eval
```

- `apps/web/app` отвечает за интерфейс и состояние пользовательского сценария.
- `apps/web/server/api` валидирует HTTP-ввод и переводит результат внешнего сервиса в продуктовый контракт. CV-логика здесь не размещается.
- `apps/web/shared/contracts` — единственный источник форм ответов между слоями.
- `services/importer` — единственный writer каталога и картинок: миграции, версия датасета, картинки и превью в MinIO, привязка фото к винам.
- `services/retrieval` содержит несколько независимых FastAPI-сервисов из одного пакета `app/` (см. `services/retrieval/README.md`): `retrieval` — чисто визуальный SIFT-поиск; `retriever` — визуальный DINOv2+SIFT поиск; `ocr-retriever` — единственное место, где работает OCR (RapidOCR), отдаёт per-поле кандидатов, не резолвит вино; `ranking` — комбинирует OCR- и визуальные кандидаты в конкретный `slug` и стоит за продуктовым сканером. Ни один не знает о компонентах Nuxt, все только читают PostgreSQL и MinIO.
- `/admin` использует read-only server API Nuxt, который читает PostgreSQL напрямую: каталог, дубли исходных строк, привязку и проверку фото, состав текущего поискового индекса.
- `/astro-sommelier` использует тот же read-only PostgreSQL-каталог и выбирает карточки только из текущей сборки поискового индекса.
- `/sommelier` хранит историю локально в браузере; server API получает только ограниченное окно реплик и никогда не раскрывает ключ провайдера.

## Два контракта поиска

Продуктовый маршрут `POST /api/scans` (Nuxt) вызывает `ranking`'s `/v1/search`, который возвращает `matched` или `not_found` (без `uncertain` — у ранжирования бинарный порог уверенности, см. ниже), карточку, диагностические оценки и версии в том же контракте `ScanResponse`, что и раньше отдавал `retrieval`. Кандидаты могут содержать `wine` для ручного выбора в UI. Отдельный оценочный маршрут `retrieval`'s `/v1/eval/predict` (чисто визуальный, не через ranking) возвращает плоский JSON `{"slug":"..."}`; при пустой выдаче slug — пустая строка.

## OCR, визуальный поиск и объединение кандидатов

OCR и визуальный поиск — не единый блендированный скор внутри одного сервиса (как было раньше), а два независимых источника доказательств, каждый со своей зоной ответственности, объединяемые только на этапе ранжирования (`services/retrieval/app/ranking.py`). Общий стракт для обоих — `app/label_fields.py`: `RetrievalFields` с полями `name`/`winery`/`grape_varieties`/`year`/`abv`/`category`/`color`/`region`/`slug`, у каждого — ранжированный список кандидатов `(значение, оценка 0..1)`.

**OCR (`app/ocr.py`, `app/ocr_retriever.py`, сервис `ocr-retriever`).** RapidOCR 3.9: детекция PP-OCRv6 + кириллическое распознавание PP-OCRv5, ONNX на CPU, модели запечены в образ. Один проход по полному кадру с учётом EXIF: на фикстурах он читает не меньше, чем кроп label_prep, а Tesseract на тех же фото почти ничего не читал. Латинские двойники кириллицы (`KPACHOE`, `ДЕHИCOB`, `3AKAT`) складываются обратно в кириллицу. Возвращает строки текста, confidence и координаты. `ranking` вызывает сервис по HTTP параллельно с `retriever`; если недоступен один из двух, скан идёт по второму, если оба — 503. Для полей с закрытым словарём каталога (name/winery/grape_varieties/category/color/region) — fuzzy-поиск по всем различным значениям поля в каталоге (`app/field_vocabulary.py`), топ-10 по оценке. Для year/abv — все прочитанные значения (не одно доверенное), оценка = confidence строки OCR. OCR никогда не резолвит вино сам.

**Визуальный поиск (`app/retriever.py`, сервис `retriever`).** DINOv2-эмбеддинг + SIFT/FLANN голосование + RANSAC геометрическая проверка, комбинированный скор `0.45·SIFT + 0.55·embedding`. Отдаёт только одно поле — `slug`, топ-10 кандидатов: это прямое доказательство идентичности вина, разложение на текстовые поля было бы придуманным сигналом.

**Ранжирование (`app/ranking.py`, сервис `ranking`).** Для каждого вина каталога — взвешенное среднее по полям, где есть кандидаты (отсутствующие опциональные поля не понижают скор); побеждает вино с максимальным скором. `matched` требует `score > MATCH_THRESHOLD` (переменная окружения `RANKING_MATCH_THRESHOLD`, по умолчанию 0.45), ненулевого свидетельства по названию (OCR) или визуальному `slug` и отсутствия ничьей с вторым кандидатом; иначе — честный `not_found`, без промежуточного статуса. Общие поля (винодельня, сорт, категория, цвет, регион, год) влияют на порядок, но сами совпадение не дают. Веса полей и порог — неоткалиброванные заглушки (см. комментарии в коде), пересчитать на размеченной выборке фото.

**Отладочная трасса (`app/scan_debug.py`).** При `RANKING_DEBUG=true` (по умолчанию) ответ `/v1/search` сервиса `ranking` содержит поле `debug` (контракт `ScanDebug` в `apps/web/shared/contracts`): превью кадра, визуальной и OCR-веток label_prep с метриками, кандидаты OCR по каждому полю (до 10), top-10 ретривера с inliers/matches и top-10 ранжирования с вкладом каждого поля. На странице результата его показывает раскрывающаяся панель `ScanDebugPanel` — и при найденном вине, и без него. Трасса не меняет скоры; единственное, что она пересчитывает, — кроп label_prep для превью; превью передаются как JPEG data URL (~100 КБ на ответ).

Пороги эвристические: калибровки на размеченных полевых фото пока нет. Синтетическая оценка и HTTP smoke не доказывают реальную точность.

## Текущий поток

1. Пользователь выбирает фото через файловый input с `capture="environment"`.
2. Клиент проверяет тип и размер, создаёт локальный preview и отправляет `FormData` в `/api/scans`.
3. Nuxt server route повторно валидирует файл.
4. При `NUXT_PUBLIC_SCAN_MODE=mock` маршрут возвращает маркированную демонстрационную карточку.

Астрологический сценарий изолирован публичным runtime-флагом `NUXT_PUBLIC_ASTRO_ENABLED`. Проверка выполняется во всех точках входа: навигации, карточке результата, middleware страницы и серверном API. При отключении API отвечает `404`, поэтому скрытие интерфейса не является единственной защитой функции.
5. В Compose Nuxt проксирует сам запрос сканера через приватный `NUXT_RANKING_BASE_URL` в `ranking` — это финальный, объединённый результат OCR и визуального поиска. Оценочный маршрут `/v1/eval/predict` вызывается напрямую у сервиса `retrieval`.
6. Карточки получают `imageUrl` и `imagePreviewUrl` только при наличии привязки в `wine_images`. `/api/wines/{slug}/image` находит основное фото в PostgreSQL и потоком отдаёт оригинал или превью из MinIO с `ETag` по sha256 — независимо от того, попал ли эталон в поисковый индекс какого-либо из сервисов поиска.
7. Админка запрашивает пагинированный `/api/admin/wines`: Nuxt строит выдачу SQL-запросом к `wines`, `wine_images` и `index_references` текущей сборки, независимо от `retrieval`/`retriever`/`ranking`.

## Поток цифрового сомелье

1. Клиент отправляет до 11 последних реплик в `/api/sommelier/chat`; сервер проверяет длину, роли и чередование общим Zod-контрактом.
2. Сервер применяет лимит сессии и локальную проверку мата. Завершённые социальные реплики вроде благодарности или «ладно» получают короткий ответ без поиска каталога; реплика с новым винным запросом проходит дальше. Текст заблокированного сообщения не записывается в лог.
3. В `live`-режиме выбранный через runtime config AI-провайдер классифицирует весь входной диалог. Поддерживаются OpenAI, Anthropic и Google через единый AI SDK adapter.
4. Модель формирует структурированные фильтры, после чего сервер обязательно вызывает `searchCatalog`. Тип вина ограничен реальными категориями базы; описательные слова ищутся русским полнотекстовым поиском. Если они обнулили выдачу, поиск повторяется без них, но сохраняет тип вина, регион, сорт и оттенок. Полностью нефильтрованный fallback запрещён.
5. Структурированный ответ содержит до трёх `slug`. Сервер принимает только `slug`, реально возвращённые поиском в текущем запросе, и повторно классифицирует текст ответа. Если модель проигнорировала непустую отфильтрованную выдачу, сервер показывает до трёх найденных карточек с нейтральным текстом.
6. В `mock`-режиме те же продуктовые состояния воспроизводятся локально и всегда маркируются в UI и API.

## Данные и индексы

Состояние хранится только в PostgreSQL (с pgvector) и MinIO. При каждом `docker compose up` одноразовый `importer` применяет миграции `db/migrations` и вычисляет `dataset_version` — хэш CSV, томов RAR, `db/image-overrides.csv` и версий алгоритмов привязки и превью. Если версия совпадает с последним успешным `import_runs`, работа пропускается. Иначе:

- оригиналы читаются из RAR по одному и кладутся в MinIO под sha256 содержимого вместе с превью; неизменный архив не перечитывается;
- каталог, привязка фото, ручные исправления и журнал проблем пишутся в PostgreSQL одной транзакцией.

Индексаторы работают по `dataset_version`. `retrieval-index` сохраняет `sift-v3/{version}.npz` в MinIO и регистрирует сборку в `index_builds`/`index_references`. `retriever-index` так же сохраняет SIFT-часть `retriever-v2`, а эмбеддинги DINOv2 пишет в `image_embeddings` (pgvector) по ключу sha256 картинки и модели, поэтому пересчитываются только новые картинки. Сервисы поиска при старте скачивают сборку для текущей версии. Ретривер ищет ближайшие эмбеддинги точным запросом pgvector в пределах своей сборки.

Для разработки web монтирует рабочую директорию проекта вместе с `.git` из хоста. Зависимости и генерируемые типы Nuxt живут в отдельных Docker volumes; Git использует SSH-настройки хоста или личный ключ через read-only mount. Entrypoint готовит права для UID/GID из локального `.env` перед запуском dev-сервера. Обычный `docker compose exec web sh` также открывает shell от этого пользователя; `psql` внутри него подключается к PostgreSQL. Постоянные тома — только `postgres-data`, `minio-data` и `retriever-models`.

## Инварианты

- Аналог не называется точным совпадением.
- `score` не называется вероятностью; `calibratedProbability` появляется только после калибровки.
- Инфраструктурная ошибка не превращается в `not_found`.
- Браузер не обращается к CV-сервису напрямую.
- Браузер не обращается к LLM-провайдеру напрямую; приватные ключи существуют только в server runtime config.
- AI не может вернуть карточку по `slug`, отсутствующему в результате последнего вызова каталога.
- Базовая карточка и локальные сохранения работают без LLM.
