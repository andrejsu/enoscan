# Архитектура Vinolog

## Границы системы

```text
Мобильный браузер
      ├─ multipart/form-data ──► Nuxt scans API ──► Retrieval API (FastAPI)
      │                                                ├─ Tesseract → catalog text candidates
      │                                                └─ SIFT / FLANN + RANSAC → joint ranking
      └─ JSON chat ───────────► Nuxt sommelier API ──► AI provider
                                      │                    (server-side only)
                                      └─ parameterized SQL tool
                                                   │
                                                   ▼
                                              PostgreSQL catalog
```

- `apps/web/app` отвечает за интерфейс и состояние пользовательского сценария.
- `apps/web/server/api` валидирует HTTP-ввод и переводит результат внешнего сервиса в продуктовый контракт. CV-логика здесь не размещается.
- `packages/contracts` — единственный источник форм ответов между слоями.
- `services/retrieval` содержит поиск конкретного `slug`; он не знает о компонентах Nuxt.
- `/admin` использует read-only server API для просмотра каталога, дублей исходных строк и состояния привязки эталонных изображений.
- `/sommelier` хранит историю локально в браузере; server API получает только ограниченное окно реплик и никогда не раскрывает ключ провайдера.

## Два контракта поиска

Продуктовый маршрут `/v1/search` возвращает `matched`, `uncertain` или `not_found`, карточку, диагностические оценки и версии. Кандидаты могут содержать `wine` для ручного выбора в UI; такой выбор обозначается отдельно от автоматического совпадения. Оценочный маршрут `/v1/eval/predict` возвращает плоский JSON `{"slug":"..."}`; при пустой выдаче slug — пустая строка. Оба маршрута используют один SearchService и индекс.

## OCR и объединение кандидатов

Tesseract остаётся движком по умолчанию (`rus+eng`, PSM 6, grayscale/CLAHE). Возвращает слова, confidence и координаты в декодированном изображении с учётом EXIF. Год принимается как признак только при контексте урожая; крепость извлекается с единицей измерения и остаётся внутренней диагностикой. Эти значения не записываются в каталог.

При старте сервис загружает полный каталог из PostgreSQL, включая позиции без эталона. Текстовый поиск добавляет до 20 кандидатов к 24 визуальным кандидатам; доступные эталоны проходят RANSAC. Объединение выполняется по slug. Насыщение геометрического score заменено плавной шкалой, одинаковые прочитанные слова не дают преимущества коротким названиям. Год даёт мягкую поправку, не удаляет кандидатов. Вино без геометрического подтверждения не получает `matched`; малый отрыв лидеров и противоречие года требуют уточнения.

`OCR_TIMEOUT_SECONDS` (по умолчанию 2) ограничивает вызов Tesseract. Ожидаемый сбой OCR оставляет визуальный поиск; ошибки декодирования/индекса не маскируются. `OCR_PSM=11`, `OCR_PREPROCESS=false` и `OCR_RETRY=true` доступны для экспериментов. Повтор ограничен одной сомнительной строкой с цифрами и остатком бюджета. Координаты текста не считаются сегментацией этикетки.

Внутренняя диагностика `ProductResult.diagnostics` доступна локальному оценочному скрипту и не отправляется браузеру или в обычные логи. Пороги эвристические: калибровки на размеченных полевых фото пока нет. Синтетическая оценка и HTTP smoke не доказывают реальную точность.

## Текущий поток

1. Пользователь выбирает фото через файловый input с `capture="environment"`.
2. Клиент проверяет тип и размер, создаёт локальный preview и отправляет `FormData` в `/api/scans`.
3. Nuxt server route повторно валидирует файл.
4. При `NUXT_PUBLIC_SCAN_MODE=mock` маршрут возвращает маркированную демонстрационную карточку.

Астрологический сценарий изолирован публичным runtime-флагом `NUXT_PUBLIC_ASTRO_ENABLED`. Проверка выполняется во всех точках входа: навигации, карточке результата, middleware страницы и серверном API. При отключении API отвечает `404`, поэтому скрытие интерфейса не является единственной защитой функции.
5. В Compose Nuxt проксирует запрос через приватный `NUXT_RETRIEVAL_BASE_URL`; retrieval возвращает продуктовый результат и ту же top-1 позицию использует оценочный маршрут.
6. Админка запрашивает пагинированный `/v1/catalog`: PostgreSQL остаётся источником карточек и числа дублей, а загруженный retrieval-индекс добавляет статус и диагностику связи с эталонным изображением.

## Поток цифрового сомелье

1. Клиент отправляет до 11 последних реплик в `/api/sommelier/chat`; сервер проверяет длину, роли и чередование общим Zod-контрактом.
2. Сервер применяет лимит сессии и локальную проверку мата. Завершённые социальные реплики вроде благодарности или «ладно» получают короткий ответ без поиска каталога; реплика с новым винным запросом проходит дальше. Текст заблокированного сообщения не записывается в лог.
3. В `live`-режиме выбранный через runtime config AI-провайдер классифицирует весь входной диалог. Поддерживаются OpenAI, Anthropic и Google через единый AI SDK adapter.
4. Модель формирует структурированные фильтры, после чего сервер обязательно вызывает `searchCatalog`. Тип вина ограничен реальными категориями базы; описательные слова ищутся русским полнотекстовым поиском. Если они обнулили выдачу, поиск повторяется без них, но сохраняет тип вина, регион, сорт и оттенок. Полностью нефильтрованный fallback запрещён.
5. Структурированный ответ содержит до трёх `slug`. Сервер принимает только `slug`, реально возвращённые поиском в текущем запросе, и повторно классифицирует текст ответа. Если модель проигнорировала непустую отфильтрованную выдачу, сервер показывает до трёх найденных карточек с нейтральным текстом.
6. В `mock`-режиме те же продуктовые состояния воспроизводятся локально и всегда маркируются в UI и API.

Docker Compose перед запуском web один раз распаковывает локальный RAR5 с медиа Strapi, CSV-каталог и `eval.zip` в постоянный том `vinolog_dataset`. Затем `db-import` транзакционно загружает все строки CSV и индекс путей медиа в PostgreSQL с маркером импорта. База хранится в отдельном постоянном томе; retrieval монтирует медиа только для чтения, а Nuxt получает результат и проксирует эталонное изображение найденной карточки через приватный HTTP API.

Для разработки web монтирует рабочую директорию проекта вместе с `.git` из хоста. Зависимости и генерируемые типы Nuxt живут в отдельных Docker volumes; Git использует SSH-настройки хоста или личный ключ через read-only mount. Entrypoint готовит права для UID/GID из локального `.env` перед запуском dev-сервера. Обычный `docker compose exec web sh` также открывает shell от этого пользователя; `psql` внутри него подключается к PostgreSQL. Производный SIFT-индекс хранится отдельно; `pgvector` появится вместе с embedding-моделью, если измерения подтвердят пользу.

## Инварианты

- Аналог не называется точным совпадением.
- `score` не называется вероятностью; `calibratedProbability` появляется только после калибровки.
- Инфраструктурная ошибка не превращается в `not_found`.
- Браузер не обращается к CV-сервису напрямую.
- Браузер не обращается к LLM-провайдеру напрямую; приватные ключи существуют только в server runtime config.
- AI не может вернуть карточку по `slug`, отсутствующему в результате последнего вызова каталога.
- Базовая карточка и локальные сохранения работают без LLM.
