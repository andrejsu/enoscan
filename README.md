# Vinolog — сканер российских вин для платформы «Своё Вино»

Покупатель фотографирует этикетку у полки, и через 2–3 секунды на телефоне открывается карточка именно этого вина из каталога «Своё Вино»: производитель, регион, сорта, описание. Без экрана с вариантами. Если вина в каталоге нет, сервис честно говорит об этом и предлагает похожие вина. После скана пользователь может сохранить сочетание с блюдом, подобрать вино с цифровым сомелье или построить винный тур.

Решение работает локально, без GPU и без внешних API: визуальный поиск и OCR идут на CPU, LLM нужна только сомелье в live-режиме.

| | |
|---|---|
| Публичный набор кейсодержателя (`eval.zip`) | **100 %** — 3 из 3 |
| Размеченный набор из 10 фото (набор настройки) | **100 %** — 10 из 10, F1 1,0 |
| Вина вне каталога: честное «не найдено» | **93 %** — 28 из 30 |
| F1 top-1 / F1 top-5, 78 фото | **0,851 / 0,872** |
| Отрыв top-1 от top-2 (медиана) | верные ответы **0,174**, ошибочные 0,021 |
| Время ответа | p50 **2,0 с**, p95 2,6 с, 96 % запросов быстрее 3 с |
| Скрипт кейсодержателя | совместим: `POST :8080/v1/eval/predict` → `{"slug":"..."}` |

## Возможности

**Сканер** (`/`). Фото с камеры или из галереи (JPEG, PNG, WebP до 10 МБ) → одна карточка вина. Пайплайн распознавания объединяет два независимых источника: визуальный поиск по эталонным фото каталога (DINOv2 + SIFT/RANSAC) и чтение текста этикетки (RapidOCR). Затем финальный кандидат сверяется с прочитанным текстом, чтобы отличить почти одинаковые этикетки разных урожаев, категорий и уровней сахара. Сервис отвечает `matched` только при заметном отрыве лидера от второго вина, иначе — честное «не найдено».

**Вина нет в каталоге.** Вместо ложного совпадения сервис показывает до трёх вин каталога, связанных с этикеткой, — той же линейки или той же винодельни с тем же сортом, категорией или сахаром — и объясняет связь и расхождение («другой урожай», «другой цвет»). Аналог никогда не выдаётся за точное совпадение.

**После скана** — функции для удержания пользователя:

| Функция | Страница | Что делает |
|---|---|---|
| Мои сочетания | `/pairings` | Сохранить вино из карточки вместе с блюдом и вкусовыми впечатлениями; хранится в браузере |
| Цифровой сомелье | `/sommelier` | Диалог о выборе вина к блюду или событию; рекомендует только вина, реально найденные SQL-поиском по каталогу |
| Винные туры | `/tours` | 16 программ виноделен Крыма и Краснодарского края на Яндекс Картах, автомобильный маршрут и ИИ-планировщик |
| Астро-сомелье | `/astro-sommelier` | Развлекательный подбор вина по знаку зодиака; отключается флагом |

**Каталог** (`/admin`) — read-only инструмент проверки импорта: версия датасета, привязка фото к винам, подозрительные привязки, состав поискового индекса.

Интерфейс mobile-first, в стилистике портала «Своё Вино».

## Быстрый старт

### Требования

| | Минимум | Рекомендуется |
|---|---|---|
| CPU | 4 ядра x86-64 с AVX2 или Apple Silicon | 8+ ядер |
| Память, выделенная Docker | 8 ГБ | 10 ГБ |
| Диск | 30 ГБ свободно, SSD | 50 ГБ NVMe |

На macOS и Windows выставьте в Docker Desktop → Settings → Resources не меньше 8 ГБ памяти и все ядра: значений по умолчанию не хватит. Скрипт кейсодержателя требует `bash`, `curl`, `jq` и `awk` на хосте (на Windows — WSL 2). Подробный расчёт ресурсов — в [ARCHITECTURE.md](ARCHITECTURE.md#требования-к-железу).

### 1. Данные

Положите файлы кейсодержателя в `data/dataset/`:

```text
data/dataset/
├── prod-svoe-vino-strapi.part1.rar
├── prod-svoe-vino-strapi.part2.rar
├── prod-svoe-vino-strapi.part3.rar
├── strapi_output0709.csv
└── eval.zip                 # необязательно: публичные фото для проверки
```

Каталог `data/` исключён из Git.

### 2. Запуск

```bash
cp .env.example .env         # необязательно: без .env действуют значения по умолчанию
docker compose up --build -d
docker compose ps            # все сервисы running/healthy, importer и *-index — exited (0)
```

Первый запуск импортирует каталог и фото (≈ 5 мин), строит SIFT-индекс (≈ 2 мин) и эмбеддинги DINOv2 (≈ 7 мин). Повторные запуски видят, что версия данных не изменилась, и проходят эти шаги за секунды. Интернет нужен только при первой сборке: модели запекаются в образы и тома.

### 3. Проверка

```bash
curl -s http://127.0.0.1:8080/health     # {"status":"ok"}
curl -s -F image=@/путь/к/фото.jpg http://127.0.0.1:8080/v1/eval/predict
```

| Адрес | Что там |
|---|---|
| http://localhost:3000 | Веб-интерфейс сканера |
| http://127.0.0.1:8080/docs | Swagger сервиса распознавания |
| http://127.0.0.1:8080/v1/eval/predict | Маршрут для скрипта кейсодержателя |
| http://127.0.0.1:9001 | Консоль MinIO (`vinolog` / `vinolog-secret`) |
| localhost:5433 | PostgreSQL (`vinolog` / `vinolog`) |

Лучше всего работает кадр, где этикетка занимает большую часть изображения, без сильных бликов, с читаемыми названием и годом.

## Проверка скриптом кейсодержателя

Скрипт `participant_test.sh` отправляет фото по одному в поле `image` и ждёт не дольше 10 секунд на фото. Сервис отвечает плоским JSON `{"slug":"wine-slug"}` на порту 8080 — это адрес скрипта по умолчанию.

```bash
# 1. Распаковать публичный набор (один раз)
unzip -q -o data/dataset/eval.zip -d data/eval -x '__MACOSX/*'

# 2. Прогреть сервис: первые запросы на холодных моделях идут 3–4 с
for f in data/eval/queries/*; do
  curl -s -o /dev/null -w "$f %{time_total}s\n" -F image=@"$f" http://127.0.0.1:8080/v1/eval/predict
done

# 3. Прогон — строго как в README кейсодержателя
cd data/eval
rm -f predictions.jsonl      # скрипт не перезаписывает существующий файл
./participant_test.sh \
  --images-dir ./queries \
  --manifest ./queries.tsv \
  --endpoint 'http://127.0.0.1:8080/v1/eval/predict' \
  --output ./predictions.jsonl
cat predictions.jsonl
```

Для закрытого набора меняются только `--images-dir` и `--manifest`.

**Неуверенный ответ.** Если сервис не уверен или вина нет в каталоге, он возвращает пустой `slug`, и скрипт записывает `null` (политика `RANKING_EVAL_POLICY=matched`, по умолчанию). Так ложные совпадения не портят точность. Если в контрольной выборке нет вин вне каталога и `null` считается ошибкой, переключите политику на `top1` — тогда всегда отдаётся лучшее вино, не опровергнутое этикеткой:

```bash
RANKING_EVAL_POLICY=top1 docker compose up -d ranking
```

**Перед замером скорости** закройте тяжёлые приложения и не запускайте `docker stats` параллельно: OCR и визуальный поиск на пике занимают около 8 ядер, и время ответа растёт почти линейно при нехватке CPU.

## API

Сервис распознавания `ranking` (порт 8080, Swagger — `/docs`):

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/v1/eval/predict` | `{"slug":"..."}` — top-1 для скрипта кейсодержателя |
| `POST` | `/v1/search` | Продуктовый ответ: статус, карточка, top-5, уверенность, похожие вина, время по этапам |
| `GET` | `/health` | `{"status":"ok"}` или `"loading"` |

Веб-приложение (порт 3000) принимает фото на `POST /api/scans` и отдаёт фото вин на `GET /api/wines/{slug}/image[?size=preview]`. Маршруты `/v1/*`, `/health` и `/docs` сайт проксирует в `ranking`, поэтому на проде скрипт работает по адресу сайта.

Ответ `/v1/search` на фото `02eef911.webp` из публичного набора (сокращены описание, `wine` у кандидатов и `debug`):

```json
{
  "status": "matched",
  "wine": {
    "slug": "massandra-muskatel-belyy-belye-sorta-vinograda-beloe-sladkoe-16",
    "name": "Мускатель белый",
    "producer": "Массандра",
    "year": null,
    "category": "Белое",
    "color": "Янтарно-золотистый, прозрачный",
    "region": "Крым",
    "grapeVarieties": ["Белые сорта винограда"],
    "description": "Аромат мускатный, цветочный с нотами акации, мёда и персика…",
    "imageUrl": "/api/wines/massandra-muskatel-belyy-belye-sorta-vinograda-beloe-sladkoe-16/image",
    "imagePreviewUrl": "/api/wines/massandra-muskatel-belyy-belye-sorta-vinograda-beloe-sladkoe-16/image?size=preview"
  },
  "candidates": [
    {"slug": "massandra-muskatel-belyy-belye-sorta-vinograda-beloe-sladkoe-16", "score": 0.2662},
    {"slug": "muskat-avtorskoe-vino", "score": 0.1841},
    {"slug": "massandra-kokur-desertnyy-surozh-beloe-sladkoe-16", "score": 0.179},
    {"slug": "massandra-muskatel-chernyy-krasnye-sorta-vinograda-krasnoe-sladkoe-16", "score": 0.176},
    {"slug": "massandra-kagor-yuzhnoberezhnyy-saperavi-krasnoe-sladkoe-16", "score": 0.1705}
  ],
  "confidence": {"kind": "similarity", "top1Score": 0.2662, "margin": 0.0821},
  "timing": {"totalMs": 2461, "stages": {"ocr": 2435, "visual": 2019}},
  "recommendations": [],
  "version": {
    "model": "ranking-ocr-visual-v3",
    "catalog": "4b07e7675073859fb7152fe3e9c2472ffd10fbcf735ef3b7b61e8ae15c580306",
    "configuration": "margin0.03;ocr=rapidocr-3.9 PP-OCRv5 cyrillic"
  },
  "isMock": false

```

В этом json видна вся схема работы. Визуальный поиск узнаёт серию этикеток Массандры, но первым ставит Кагор «Гурзуф» (60 совпавших точек после RANSAC). OCR читает «МУСКАТЕЛЬ БЕЛЫЙ» и выдвигает своё вино. Сверка отклоняет Кагор — на этикетке «Мускатель», которого нет в его названии, — и побеждает «Мускатель белый» с отрывом 0,082 при пороге 0,03, который можно менять по env переменной.

- `status` — `matched` (найдена одна карточка) или `not_found` (уверенного ответа нет; тогда есть `guidance` и, если этикетка на что-то указывает, `recommendations`).
- `confidence.top1Score` и `confidence.margin` — оценка лидера и его отрыв от ближайшего соперника, которого этикетка не опровергает. Это не вероятность. `matched` требует отрыва не меньше `RANKING_MIN_MARGIN`.
- `candidates` — top-5 по оценке, по ним UI может показать выбор; опровергнутые этикеткой вина стоят в конце.
- При `RANKING_DEBUG=true` в ответе есть `debug` — трасса каждого этапа, которую показывает отладочная панель сканера.

F1 для top-1 и top-5 — метрика набора фото, а не одного запроса. Её считает оценочный скрипт (раздел [«Качество»](#качество)); в API каждого запроса отдаются исходные данные для неё — лидер, отрыв и top-5.

Все переменные необязательны: значения по умолчанию заданы в `compose.yaml`, шаблон — `.env.example`. После изменения `.env` пересоздайте нужный сервис: `docker compose up -d <сервис>` (`docker compose restart` переменные не перечитывает).

## Качество

Метрики считаются так же, как у кейсодержателя: `scripts/eval_ranking.py` отправляет фото в `/v1/eval/predict` по одному (поле `image`, лимит 10 с), пишет `predictions.jsonl` в формате организатора и дополнительно запрашивает `/v1/search` для top-5 и отрыва. Определения метрик — в docstring скрипта.

- **Доля совпадений** — ответ равен правильному slug; фото вина вне каталога засчитывается, только если ответ `null`.
- **F1 top-1** — precision по данным ответам и recall по фото вин из каталога.
- **F1 top-5** — ответ засчитывается, если правильное вино есть в top-5.

### Результаты

| Набор | Фото | Результат |
|---|---|---|
| Публичный набор кейсодержателя, `participant_test.sh` | 3 (1 вино каталога, 2 вне его) | 3 из 3, 2,0–2,3 с на фото |
| Размеченный набор `configs/labeled-photos.tsv` | 10 (8 / 2) | 10 из 10, F1 1,0, p95 2,3 с |

Основной набор для оценки — 78 реальных фото у полки из `data/Реальные фото`: 48 вин каталога и 30 вин вне его, разметка ручная по этикетке и карточке.

| Версия пайплайна | Доля совпадений | F1 top-1 | F1 top-5 | p95 |
|---|---|---|---|---|
| Базовая: визуальный поиск + OCR | 0,641 | 0,621 | — | 3,2 с |
| + исправленная привязка фото к винам | 0,667 | 0,667 | — | 3,1 с |
| + OCR v2: кроп этикетки, словарь каталога | 0,833 | 0,821 | — | 2,6 с |
| **+ OCR v3: сверка с этикеткой, сахар (текущая)** | **0,872** | **0,851** | **0,872** | **2,6 с** |

Для текущей версии: precision 0,870, recall 0,833, правильное вино на первом месте в 85,4 % случаев и в top-5 — в 87,5 %; из 30 вин вне каталога 28 получили честный `null`. Медианный отрыв верных ответов (0,174) в восемь раз больше, чем у ошибочных (0,021), — поэтому интерфейс может показывать одну карточку без экрана выбора.

Разбор 10 ошибок текущей версии: в 6 случаях правильного вина нет среди кандидатов OCR и визуального поиска, в 2 — правильное вино в top-2, но проиграло почти-дублю той же линейки, в 2 — вино вне каталога получило ложное совпадение. Главный резерв точности — полнота кандидатов, а не решающее правило (см. [ARCHITECTURE.md](ARCHITECTURE.md#известные-ограничения-и-развитие)).

Набор из 10 фото (7 фикстур и 3 фото из `eval.zip`) использовался для подбора порогов, поэтому его 10 из 10 показывает работоспособность, а обобщающую точность — набор из 78 фото.

Время ответа зависит от загрузки машины: повторный прогон 2026-09-29 на том же стенде дал ту же точность, но p95 3,7 с и 82 % ответов быстрее 3 с. Лимит скрипта в 10 с ни разу не был превышен.

## Ограничения

- **Размер выборки.** Веса и пороги подобраны на 10 размеченных фото и 147 искажённых эталонах каталога, проверены на 78 фото. На закрытом наборе цифры могут отличаться; параметры нужно перепроверять при появлении новой разметки.
- **Почти-дубли.** Вина одной линейки с одинаковой этикеткой различаются только текстом (год, категория, сахар). Если OCR этот текст не прочитал, сервис отвечает «не найдено», а не угадывает.
- **Качество каталога.** Часть фото привязана к винам по нечёткому совпадению имени файла; вино с чужим эталонным фото визуально не найти. Проблемные привязки видны в `/admin` и исправляются через `db/image-overrides.csv`.
- **Форматы.** HEIC не поддерживается, размер фото — до 10 МБ. Фото отправляется без сжатия в браузере, поэтому на медленной мобильной сети загрузка добавляет время к ответу. При этом через камеру веб интерфейса apple устройства работа стабильная. 
- **Деградация.** Если OCR или визуальный поиск не ответили за 8 с, `ranking` решает по оставшемуся источнику, и точность падает; если оба недоступны — HTTP 503.
- **Сомелье.** Реализованы адаптеры трёх провайдеров, но live-качество и стоимость не измерены с реальными ключами каждого; для демо надёжнее режим `mock`.
- **Отладка.** `RANKING_DEBUG=true` (по умолчанию локально) показывает промежуточные данные распознавания всем пользователям; на проде панель дебага выключена.

## Структура репозитория

```text
apps/web/                 Nuxt 4: мобильный интерфейс и server API
  shared/contracts/       Общие TypeScript-контракты UI и API
services/retrieval/       Python/FastAPI: сервисы распознавания ranking, ocr-retriever, retriever
services/importer/        Импорт каталога и фото в PostgreSQL и MinIO
db/                       Миграции PostgreSQL и ручные исправления привязки фото
scripts/                  Оценка качества, аудит привязки, нормализация этикеток
configs/                  Разметка фото для оценки
reports/                  Результаты прогонов
deploy/                   Прод-стек: Compose, Caddy, Dockerfile образов
docs/engineering/         Правила кода, разработка, деплой
```

Push в `master` проверяет проект, собирает образы в GHCR и выкатывает их на VPS через GitHub Actions — см. [docs/engineering/DEPLOY.md](docs/engineering/DEPLOY.md).
